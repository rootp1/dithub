# How Dithub uses Arkiv (concrete flows)

1. **Code chunks and manifests.** On push to the default branch of a public repo under `ARKIV_CODE_MAX_BYTES`, the worker (`handlePush` in `apps/worker/src/index.ts`) runs `publishRepository`, then `uploadManifestToArkiv`: 120 KiB BLAKE3-hashed `dheet-chunk-v1` entities and one `dheet-manifest-v1` entity. Entities are tracked in `arkiv_entities` for renewal.
2. **Per-commit activity with tx hashes.** The worker first sends one `RefRegistry` anchor transaction on Sepolia per ref update, then writes one `dheet-activity-v1` entity (kind `commit`) per commit with `l1Tx` set to that transaction hash, plus a `push` entity referencing the manifest. Private repos are skipped.
3. **Repo name claims.** Creating a repo queues a `name_claim`; the worker writes a `dheet-name-v1` entity (`owner/repo` -> repoId, owner) and stores the entity key in `name_claims.arkiv_entity`.
4. **RBAC hash chain.** Each change in a public org is appended to `rbac_events` (`hash = sha256(prev || canonical(event))`) and mirrored as a `rbac` activity entity containing `prevHash` and `hash`; anyone can recompute the chain from Arkiv.
5. **Deployment history, read back in the UI/API.** `apps/worker/src/deployments.ts` follows `ReleasePublished` and `Attested` logs on Sepolia (cursor in `chain_cursors`) and writes `deploy` / `attest` activity entities under the key `sha256('dheet:deployments')`. `GET /api/deployments` (`apps/api/src/deployments.ts`) **reads them from Arkiv** (30 s cache, trusted-writer filter, newest-first, limit 100) and only falls back to the SQLite mirror, flagged `source: "sqlite-fallback"`, if Arkiv is unreachable.
   Tested live: the worker mirrored releases #1, #2 and an attestation; a full rescan created no duplicates; the API returned `source: "arkiv"`.
6. **Recovery.** `dithub arkiv-clone` (`packages/cli`) rebuilds a repository into an empty local store using only Arkiv reads, checking the manifest hash and each chunk hash; it was run against the Sepolia/Rabdi manifest (see `docs/implementation-status.md`). Rebuilding Postgres from Arkiv is planned, not implemented.
7. **Renewal.** Hourly, the worker extends entities expiring within about 30 days (`renewArkivEntities`).
